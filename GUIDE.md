# Using local models through the hub

## Now
- One LM Studio on this Mac is shared by every project and every Claude Code session through this hub. The rules live here, once; other projects get a signpost to this file.
- **Send requests to `http://localhost:1235/v1`**, the hub's gateway: the same API as LM Studio's (`/v1/chat/completions`, `/v1/models`, `/api/v0/models`, …). Never directly to LM Studio's port 1234.
- **Attribution is automatic.** The gateway derives your project from the client process's working folder and your Claude Code session from Claude Code's own ids. There is nothing to register.
- **A family of replicas is one model.** With the default settings `qwen/qwen3.6-35b-a3b` runs as two replicas of 4 slots each: request it as one model and the gateway picks the replica. **A batch should keep as many requests in flight as the loaded replicas have slots** (the `status` tool and `localmodels` report the number); the gateway queues the rest.
- **Bulk reading jobs go to local agents** (the `local-models` MCP tools `ask` and `batch`, or `localmodels ask`), not to multi-agent Claude workflows. Treat their answers as leads to verify, not verdicts.
- **Never stop LM Studio's server.** Before unloading or reloading a model, run `swap_check` (or `localmodels swapcheck`). If it names anyone, don't swap.
- **If a model crashes, the instance manager reloads it** within a minute (at most 3 reloads per instance per hour); the other replicas keep serving meanwhile, and a request that was in flight is resent once the model is back. You get a response, or `503` with `Retry-After` if it failed twice, never LM Studio's `400`. The instance manager also **recycles each instance before the token count at which the engine has crashed**, one instance at a time, so a long batch keeps running, and the gateway **admits requests by the context they bring** as well as by free slots, so several long conversations at once do not run an instance out of memory (a request may wait in the queue for room).
- **Interactive requests first.** When every slot is busy, the next free slot goes to a `chat` or `ask` request before queued batch requests. Send `X-Kind: chat` when a user is waiting. The priority is self-declared and cooperative, like everything here.
- **Turn LM Studio's just-in-time model loading off** (its developer settings). The gateway never needs it; with it on, a request for a model with no instance loaded could make LM Studio load one with its own settings. The gateway rejects such requests (`503`) rather than forward them, and the instance manager recycles an instance whose load parameters differ from its family's, but off is simpler.
- **Other Macs (peers).** A host linked by Thunderbolt can run the same hub and serve replicas of a family: the gateway routes requests to a peer's free slots by the slot order in *Peers* (batches spread across hosts, interactive requests stay local first), and responses return through this gateway. Clients change nothing. *Peers*, below, has the rules and the setup.
- **Dashboard:** **http://localhost:1235** (`localmodels open`): every project and session using the models, each instance's slots and its tokens since load against its recycle threshold, memory as one pool across this Mac and its peers, charts over the last 15 minutes to 24 hours. In a terminal: `localmodels` (a short status) or `localmodels dash` (live).

## Where to send requests
- Base URL `http://localhost:1235/v1` for any OpenAI-compatible client (the Python `openai` package, `curl`, LangChain, an app's "custom endpoint" field), or `http://localhost:1235` for an Anthropic-compatible client (the `anthropic` package's `base_url`; it calls `/v1/messages`). LM Studio's own REST API works the same way at `/api/v1/...`. The API key can be anything.
- Every API goes through the same admission control, and its token counts feed the dashboard and the recycle accounting alike. When the gateway itself rejects a request (`503` while queued, `409` during a swap), the error on `/v1/messages` has Anthropic's error shape (`overloaded_error` for a `503`), so Anthropic's SDKs retry it; on the other paths it stays `{"error": "..."}`.
- The gateway forwards everything to LM Studio unchanged, streaming included. What it adds is admission control: all clients together never send a model more concurrent requests than it has slots (its *Max Concurrent Predictions*), nor more context in flight than each instance's memory allows (*Crash recovery*, below), so a request queues instead of piling up inside LM Studio until it times out or the engine runs out of memory.
- **Replicas.** A family in `models.json` is loaded as `<id>`, `<id>:2`, … with the same context length and slot count. A request for the family id goes to the first replica with a free slot (fill-first: replica 1's slots fill before replica 2's); a request naming one instance goes to that instance while it is loaded, else to its siblings. The response names the model requested.
- **Measured** (Apple M5 Max, 128 GB; LM Studio 0.4; Qwen3.6-35B-A3B 8-bit, 65,536 context, 4 slots per instance): on short outputs, 4 concurrent requests generated 209 tokens/s in aggregate and 8 concurrent on two replicas 252; on long prompts with long strict-JSON outputs (`tools/loadbench.py`), two replicas with 8 slots generated 193 tokens/s with every slot busy against 156 for one instance with 4 — 23% more aggregate throughput, at 1.7 times the per-request latency (median 177 s against 106 s). Two replicas serve batches; an interactive user is better served by the queue's interactive-first priority than by a third replica.
- The instance manager loads a family's missing replicas whenever its first instance is loaded, if they fit in memory. It never loads a model from nothing (a Mac with no model loaded stays free), except after a crash, and never unloads one for being idle; it does recycle an instance (unload and reload it with no request in flight on it) before the token count at which the engine has crashed, and reloads an instance whose load parameters differ from its family's. The settings live in `~/Library/Application Support/LocalModels/models.json` (`families`: `copies` (the replica count), `context`, `parallel`, `recycle`, `admit`; `batch_at_once`; `headroom_gb`); a fresh install writes it fitted to the Mac's memory and downloaded models, starting from the repo's measured default `localmodels/models.json`.
- If LM Studio's server is down (LM Studio stops it when the model is changed in its window), the gateway starts it and retries once. It never starts a server that is already up: that restarts it and drops every request in flight. If the gateway itself is down, `localmodels start` starts it. Code that must keep working without the hub can use `llmshare.post`: through the gateway when it is up, direct to LM Studio holding a slot lock when it is not. (`LMSTUDIO_URL` is LM Studio's own address for the hub's code, port 1234, never the gateway's; a project's code finds the gateway at `llmshare.HUB`.)
- **Never hold a slot lock of your own (`llmshare.slot`) for a request you send through the gateway.** The gateway takes a slot for it, and the two would deadlock.
- A client that closes its connection while its request is queued is dropped, not forwarded (status `499`, the log notes `client closed`); one that closes during a long response makes the gateway close its upstream connection too, which stops generation.
- A client that declares its timeout (`X-Timeout: <seconds>`; `llmshare.post` sends its own) gets `503` with `Retry-After` at nine tenths of it, so the gateway's queue wait never outlives the client's.

## Request attribution (optional)
- **Three names, three levels.** The *project* is who is using the models (shown on every screen); a *batch* (`X-Run`) is one named run of work inside a project; a *job* is the phase in `X-Step` (`extract files 8 of 360`). "Call this project research" sets the project's name (the `name` tool, below), not `X-Run`.
- **A project names itself once:** the `local-models` MCP tool `name` (`name="research"`, `formerly=["lab"]` for an `X-Project` its scripts used to send, `private=true` to hide its session titles). It covers the project's folder and every name listed, for past requests too, on every screen at once; no restart. From a terminal: `localmodels name project <as seen> <shown>`.
- Nothing is required. The project is the first folder under `~/Documents` (or `~/Projects`, `~/Developer`, …) that the client process runs in, so a worktree counts as its project. The Claude Code session comes from the ids Claude Code sets in every shell and tool it starts.
- To set the project explicitly: header `X-Project: <name>`, or a path prefix (`http://localhost:1235/p/<name>/v1`, for apps that only accept a base URL).
- Request kind: header `X-Kind:` `batch`, `chat` (a user is waiting), `ask`, `eval`, `test` or `other`. The dashboard shows it, and `chat` and `ask` take priority when slots are scarce.
- Purpose: header `X-Step: reading chapter 3` (a few words). The dashboard shows it next to the request; the local agents set it themselves.

## Batch progress and ETA
- **A client running a batch declares it with three headers on each request**, from any language, no library needed. The dashboard then shows a progress bar and the ETA, and `localmodels` a one-line summary:
  - `X-Run: nightly-extract`: the run's name, identical on every request of it.
  - `X-Run-Total: 420`: the units of work in the whole run, all phases together. It may increase as the client learns more (a phase whose size is known only when the previous one ends).
  - `X-Run-Done: 17`: the units completed so far, as the client counts them.
- The client counts because only it knows what a unit is: one item may take several requests, a retry, or an agent's tool loop. Keep `X-Step` for the current phase (`extract files 8 of 360`); the dashboard shows both.
- **Without the headers**, a step of the form `<phase> N of M` still yields that phase's progress: items whose request completed count as done.
- **The ETA is measured on this Mac, never assumed:** the pace over the last 15 minutes or the last 20 units, whichever window reaches further back, so it tracks a run that speeds up or slows down. Before 3 units are done it uses the previous run of the same name; the first time a name runs, it reports *estimating* until a pace is measurable. Keep a run's name stable from one run to the next so the estimate starts right.
- A 20-minute gap between requests starts a new run of the same name. A run with no request for 15 minutes is no longer shown.
- The hub logs the run's name and the two counters with each request, nothing else about it.
- `X-Session` is a free tag for the request log (the measurement tools use it to tell runs apart).

## Long runs: leases
- The hub counts a client as using a model from its first request until two minutes after its last, so no swap unloads the model between two steps of a run. That covers most workloads with no code at all.
- A run that pauses longer, or that should report its progress on the dashboard, holds a lease:

```python
import os, sys; sys.path.append(os.environ.get('LOCALMODELS_HOME', '<where the hub is checked out>'))
from localmodels import llmshare
with llmshare.lease('<project>', [model], 'batch', log_dir=folder) as run:   # log_dir: optional, see local agents
    run.step('reading the second file')        # optional: the current step, shown on the dashboard immediately
    reply = llmshare.post('/v1/chat/completions', body, '<project>', 'batch')
```

- A lease holds the project name, the model ids, a kind and the Claude Code session if there is one. Never a prompt, a file name or any content.

## Display names
- **Every screen shows the names the operator sets:** the dashboard, `localmodels`, `localmodels log`, the terminal dash and the `status` tool. The hub records what a client or folder calls itself (`X-Project`, else its folder); `~/Library/Application Support/LocalModels/names.json` maps that to the display name at read time, so a new name applies to all history.
- `localmodels name` lists every project as recorded and as displayed, with the batches (`X-Run`), jobs (the phase in `X-Step`) and scripts it has used. Then:
  - `localmodels name project <as seen> <shown>`: the display name of a project on every screen. Several recorded names can display as one, e.g. a folder and the `X-Project` its scripts send.
  - `localmodels name batch <project> <as seen> <shown>`: a display name for one of its batches, jobs or scripts.
  - `localmodels name private <project>` (and `public`): the screens show only the names set for it, with no Claude Code session titles and no unlabeled scripts, free-text steps or batch names. A count such as `8 of 360` stays.
  - `localmodels name forget <project> [<as seen>]`: drop one label, or the whole entry.
- A client can still name itself and its batch (`X-Project`, `X-Run`); the operator's names apply on top.

## Maintenance
- **The operator schedules it:** `localmodels maintenance in 15m for 30m updating LM Studio` (or `at 20:30`, `now`, or `after-batches`, which starts once no batch has sent a request for 2 minutes). `localmodels maintenance` alone shows what is scheduled and which batches would run into it; `localmodels maintenance off` ends it.
- **Announced** (before it starts), everything works, and the hub reports it everywhere: every response from the gateway carries the header `X-Hub-Maintenance` (`announced; starts=<local time>; until=<local time>; minutes=30; why=...`), the dashboard shows it at the top and flags a batch or job whose ETA falls after the start, `localmodels` and the `status` tool report it, `/hub/health` includes it, and a Claude Code hook adds one line to every session's next prompt.
- **On**, a new request gets `503` with `Retry-After` set to the expected end, and the same header; requests already in flight complete; queued requests are refused when dequeued. The gateway never starts LM Studio's server and the instance manager performs no loads, reloads or recycles, so the hub never interferes with an operator updating or restarting LM Studio.
- **Off**, what LM Studio logged meanwhile is not read as crashes, and each model that was loaded when maintenance began is reloaded (its replicas follow).
- **A client:** read `X-Hub-Maintenance` on any response. On `announced`, finish the item in hand and do not start work that would run past `starts`. On `503` with `Retry-After`, sleep that long and resume where it left off; do not count it as a failure. The hub's own local agents already retry a `503` for up to an hour.
- **A Claude Code session** that receives the notice does not start a local-model batch that would run into it, and tells the user.

## Swaps (unload, reload, context change)
- The simplest swap: `localmodels use <model>` (`--dry` shows the plan). It refuses while another run is using anything it would unload, unloads the rest (every replica of a family, to free the memory), and loads the model; `localmodels use <family>` restores all its replicas.
- Manually, before `lms unload`, `lms load` with another context, or a model switch: `localmodels swapcheck <model>` (exit 0 = safe), the `swap_check` tool, or `llmshare.swap_blockers([model])`. If it names a run, don't swap: report who is using it and stop. If `lms ps` doesn't respond, don't swap either. A run on one replica blocks a swap of any replica of its family.
- The gateway refuses a load or unload sent through it while another run is using the model (`409`, naming the run).

## Peers: other Macs over Thunderbolt
- **Model.** Every host runs its own hub (gateway + instance manager). The host the clients use (the front) lists peer gateways under `peers` in its settings; a host that serves as a peer sets `serve` (the address of its link listener). A family loaded on a peer is one more replica of that family: admission takes local instances first, then peer replicas, through the same admission queue (interactive requests first, then FIFO). Clients change nothing: they keep sending to `http://localhost:1235`, and responses name the model requested.
- **Capacity.** The front polls each peer's `GET /hub/peer` every 2 s: per family, its instances, total slots, busy slots, and how many of those this front holds, and its context budget, the context in flight there and how much of it this front sent (*Crash recovery*, admission by context size). The front never has more requests in flight on a peer than `slots − (busy − this front's)` at the last poll, and sends a request there only while it fits that peer's budget beside what others hold there (or the peer has nothing in flight); the peer admits it again by its own budget. `localmodels`, the `status` tool and `llmshare.at_once` include that capacity, so a batch sized by them also fills the peers.
- **Slot order.** Batch requests (every kind except `chat` and `ask`) fill each host's first instance before a second instance on any one host: local instance 1, the peers' first instances, local instance 2, then the remaining peer slots. Interactive requests (`chat`, `ask`) take local instances first (lowest per-request latency) and peer replicas only when local slots are full.
- **Measured** (Qwen3.6-35B-A3B 8-bit, LM Studio 0.4, MLX; `tools/loadbench.py` extraction load: 16 requests, long prompts, strict-JSON outputs, thinking off, up to 10,000 tokens each; peer on a Thunderbolt 5 cable):

  | | output tokens/s, all slots busy | per request | median latency | p90 |
  |---|---|---|---|---|
  | Apple M5 Max (128 GB), 1 instance × 4 slots | 156.4 | 39.1 | 106 s | |
  | Apple M5 Max, 2 instances × 4 slots | 192.6 | 24.1 | 177 s | |
  | MacBook Pro M4 Pro (16-core GPU, 48 GB), 1 instance × 4 slots | 73.3 (70.5 wall-clock; 57.9 prompt tokens/s) | 18.3 | 237 s | 282 s |

  The peer recalled 1,490 of 1,492 planted figures (0 empty, 0 errors, 0 fabricated), the same accuracy as the M5 Max. One peer instance delivers about 47% of one M5 Max instance, and adds nearly all of it on top of the M5 Max's two instances (192.6 + 73.3 ≈ 266 tokens/s, +38%), since its GPU and memory bandwidth are independent; a second instance on the same host added 23%. Hence the slot order: independent hosts before stacked instances for batches, the fastest local slot for interactive requests.
- **Model identity.** A peer's instances are replicas only when they match this host's fingerprint: the family id in settings, the loaded variant (`lms ps --json` `selectedVariant`, e.g. `qwen/qwen3.6-35b-a3b@8bit`), size in bytes, format, and a digest of the model definition (`~/.lmstudio/hub/models/<key>/model.yaml` and `manifest.json`, which carry the prompt template, including the thinking switch, and the sampling config). Another quantization under the same key is another model. Weights copied without their definition load under another key with no template, and strict-JSON outputs come back empty. A family never loaded on this host has no local fingerprint; `"variant": "<key>@<quantization>"` in the family's settings pins the accepted variant. The dashboard shows why a replica is excluded.
- **Attribution.** The front forwards `X-Project`, `X-Session`, `X-Kind`, `X-Step`, `X-Run`, `X-Run-Total` and `X-Run-Done`, plus `X-Hub-From` (its gateway name). The peer logs the request under that project with `from: <front>`, holds a lease for it (a swap on the peer is refused while the front's batch uses the model, and the refusal names the front), and shows it on its own dashboard. The front logs it with `copy: "<family> on <peer>"` and `peer: <name>`, so the front's recycle accounting never counts peer tokens against a local instance.
- **Failure handling.** If a peer cannot take a request (ECONNREFUSED, maintenance, auth failure, or no free slot within 5 s: the front sends `X-Timeout: 5`), the peer responds before any byte reaches the client and the front requeues the request locally; the request log notes `requeued locally: ...`. An unreachable peer is polled again with exponential backoff (2 s, 4, 8 … 60 s); an auth failure is not retried until the token or settings change, or 5 min pass; a peer in maintenance is excluded until its window ends; three failed requests within 60 s back a peer off as if unreachable. TCP keepalive on peer connections detects a dead link mid-response within about 25 s; a stream already started then ends with an error event in its API's format.
- **Per-host scope.** Maintenance, recycling, crash recovery and the instance manager stay local to each host. This host's maintenance still rejects new requests even when a peer is up. Requests received over the link are served locally only (no multi-hop routing).
- **Connections to a peer.** The front connects to a peer only through the interface whose subnet holds the peer's address, bound to it (`IP_BOUND_IF`) and from its own address there, and follows no redirect: with the cable out the bridge has no address, so the peer is down ("not on a subnet of this Mac's interfaces") and neither the token nor a request leaves by another route. A peer named by host name is used only when the name resolves onto such a subnet.
- **Link listener.** A host with `serve` set binds a second listener on that address, bound to its interface (`IP_BOUND_IF`); an unspecified address (`0.0.0.0`, `::`) or a name is refused, since it would listen on every interface. It accepts only requests carrying the shared token (`X-Hub-Token`, constant-time compare), rejects any with an `Origin` header, and serves only inference endpoints, the model list, `/hub/peer` and `/hub/health`; loads, unloads, recycles, maintenance and the dashboard are loopback-only. The token is one secret for the whole set of hosts, in `~/Library/Application Support/LocalModels/peer-token` (mode 0600), never in the repo or settings and never printed. It crosses the cable over plain HTTP, so the link assumes a direct cable between trusted hosts.
- **LM Link** (LM Studio's machine linking: preview, over its own Tailscale network, requires an LM Studio account) lets `localhost:1234` reach a model loaded on another machine. It does not load-balance one model across machines (with the model loaded on both, requests stay local), tracks no slots, and routes over whatever path its network picks rather than the Thunderbolt Bridge. The hub does not use it, and excludes from its listing any model LM Link reports from another machine (`lms ps --json` rows with `deviceIdentifier` set), so LM Link can stay on or off on either host.

### Setting up a peer
Example: the front (here) and a peer (a 48 GB MacBook Pro) joined by a Thunderbolt cable. Steps marked **(manual)** need someone at that host: an administrator password, or a click in a dialog.

1. **Static addresses on the Thunderbolt Bridge (manual, both hosts).** One cable gives each host two link-local interfaces (`bridge0` and a virtual "Ethernet Adapter"); traffic to a 169.254 address may route via the slower one (measured: about 42 MB/s against 1.7 GB/s over `bridge0`), and those addresses change on every reboot. Assign each host a static IPv4 address on the bridge, in a dedicated subnet, e.g. 192.168.213.1 here and 192.168.213.2 on the peer: System Settings → Network → Thunderbolt Bridge → Details → TCP/IP → Configure IPv4: Manually, subnet mask 255.255.255.0, no router. Or: `sudo networksetup -setmanual "Thunderbolt Bridge" 192.168.213.2 255.255.255.0` (on the peer; `.1` here). Verify: `ifconfig bridge0 | grep "inet "` on each host; from here, `route -n get 192.168.213.2` reports `interface: bridge0` and `ping -c 3 192.168.213.2` replies.
2. **The hub on the peer.** Python 3.9+ (Command Line Tools: `xcode-select --install`, **manual**: one click), the repo, then `bin/localmodels install --no-claude` (omit `--no-claude` if Claude Code runs there too). Write the peer's settings (step 4) first: `install` keeps an existing settings file.
3. **The model on the peer, as LM Studio stores it.** Either download the same model in LM Studio there, or replicate it from here: `localmodels peer copy-model qwen/qwen3.6-35b-a3b <user>@192.168.213.2`, with LM Studio stopped on the peer (**manual**, or `lms daemon down` there; the command refuses while it runs). A catalog model is four artifacts, and copying fewer leaves it listed twice or loaded without its template: the definition folder (`~/.lmstudio/hub/models/<key>/`), the variant's weights folder (under the downloads folder), its two records in `~/.lmstudio/.internal/model-data.json` (the catalog model, `source.type: hub`, `transitive: false`; the weights folder, `source.type: huggingface` with its repository, `transitive: true`, `source.file` marked undefined in the superjson meta), and the default load config (`.internal/user-concrete-model-default-config/<key>.json`). `copy-model` rsyncs the folders over SSH, merges this host's two records, as LM Studio wrote them, into the peer's `model-data.json` (its other records preserved, the previous file backed up) and copies the config; `--dry` prints the plan. Verify on the peer with LM Studio running: `lms ls` lists the model once, and `lms ps --json` reports the same `modelKey` and `selectedVariant` as here.
4. **The family in the peer's settings.** On a host where two instances do not fit, `install`'s generated settings may pick another model or none. Set the family explicitly in the peer's `~/Library/Application Support/LocalModels/models.json`: one instance, the context and slots it runs with (measured on the 48 GB MacBook Pro: 65,536 and 4), and a `headroom_gb` that leaves the instance manager room to load it (`install` sets 8 on hosts with 48 GB or more, which a 35 GiB model on 48 GB never has): `"families": {"qwen/qwen3.6-35b-a3b": {"key": "qwen/qwen3.6-35b-a3b", "copies": 1, "context": 65536, "parallel": 4, "load_at_start": true, "recycle": {"tokens": 300000, "written": 150000, "soft": 220000, "before_batch": 0.5}}}, "headroom_gb": 4, "serve": {"address": "192.168.213.2"}`. `"load_at_start": true` is for a dedicated peer: at gateway start the instance manager loads the family if no instance of it is loaded, after starting llmster (`lms daemon up`) when LM Studio is not running and once the GPU wired limit and free memory allow; at most 3 attempts 30 s apart, then it reports the manual command. An instance unloaded later by an operator is not reloaded until the next gateway start.
5. **GPU wired limit on the peer (manual, sudo).** By default macOS lets the GPU wire about 75% of RAM on this host (36 GiB of 48; Metal reports 107.5 GiB, 84%, on the 128 GiB M5 Max, and the hub reads Metal's figure, `recommendedMaxWorkingSetSize`, in a process of its own); the model's 35.2 GiB (37.75 GB) plus KV cache needs more. `localmodels peer gpu-limit`, run on the peer, writes the LaunchDaemon `com.local-models.gpu-limit` (runs `/usr/sbin/sysctl iogpu.wired_limit_mb=40960` at load: total RAM minus 8 GiB, set at boot, before login and LM Studio) next to the settings and prints the four `sudo` commands that install it; on a host where it is installed, it verifies it. Until the next reboot: `sudo sysctl iogpu.wired_limit_mb=40960`, then restart LM Studio (it reads the limit at startup). The peer reports the limit, and both dashboards warn when a model exceeds it or fits only because it was raised at runtime without the LaunchDaemon.
6. **LM Studio's loading guardrail on the peer (manual, in LM Studio).** For a model that nearly fills the GPU wired limit, only Off lets `lms load` through. Measured on the 48 GB MacBook Pro: the guardrail refused every `lms load` of this model at every context, under Relaxed, under Custom 42 GB, and with `"alwaysAllowLoadAnyway": true` (which affects only the UI's "Load anyway"; lmstudio-ai/lms issue 499); with Settings → Model loading guardrails → Off (`"modelLoadingGuardrails": {"mode": "off"}`), `lms load` succeeds. The instance manager enforces `headroom_gb` itself before every load. The peer warns on both dashboards before any load is refused (guardrail on and a model above 75% of the GPU wired limit). With the guardrail on, the instance manager cannot load the model at start or on crash recovery: it reports the refusal and does not retry until the guardrail setting or `iogpu.wired_limit_mb` changes, or an operator loads it. A single-instance family is recycled only when the guardrail is Off or the instance manager has loaded it on that host once (make before break).
7. **First load on a dedicated peer.** With `load_at_start`, the instance manager loads the model when the hub's gateway starts. A login LaunchAgent from before the hub (`~/Library/LaunchAgents/com.local-models.load-at-login.plist`) keeps that job while it is installed, and the instance manager defers to it; `localmodels install` retires it (`launchctl bootout`, plist removed; script and log kept) once a family has `load_at_start`, so exactly one loader runs. Without `load_at_start`: `lms load qwen/qwen3.6-35b-a3b --identifier qwen/qwen3.6-35b-a3b -c 65536 --parallel 4 -y`.
8. **Register the peer and the token, here.** `localmodels peer add macbook 192.168.213.2` adds the peer to this host's settings, creates `peer-token` (64 hex characters, mode 0600) if missing, and prints the `ssh` command that copies it to the peer (the token is never printed). Run that command.
9. **Enable the link listener on the peer.** `localmodels peer serve 192.168.213.2` (or `serve` in its settings, step 4). The gateway binds it within 5 s; `localmodels peer` on the peer shows the listener and its interface, warning when it is not the Thunderbolt Bridge or the address is link-local. **(manual)** With the peer's application firewall on, macOS may ask whether python3 may accept incoming connections: Allow.
10. **Verify, here.** `localmodels peer test` forces a poll from the gateway and probes from the terminal. `reachable` means done. The gateway's first connection right after the link comes up can fail with EHOSTUNREACH while macOS evaluates its Local Network policy, so `peer test` polls once more before diagnosing. If the terminal still connects but the gateway reports EHOSTUNREACH, macOS Local Network privacy is blocking the gateway: it runs as a LaunchAgent, and macOS 15+ may block such a process's local-network connections with EHOSTUNREACH and no prompt. **(manual)** System Settings → Privacy & Security → Local Network → enable Python (python3), then test again.

**(manual)** With FileVault on, a rebooted peer runs nothing until someone logs in: the GPU-limit LaunchDaemon, the hub and the model load all wait for that login, and the front routes around the peer meanwhile.

`localmodels peer`, the dashboard and the `status` tool then show each peer: state, RTT and interface, its replicas as rows under the family with slots colored by project, and, at the top of the dashboard, anything an operator must fix. `localmodels peer remove <name>` and `localmodels peer serve off` revert it; the gateway rereads the settings within seconds, so none of this needs a restart.

## Crash recovery and pre-emptive recycling
**The failures.** LM Studio's MLX engine dies in two ways, each followed by a segmentation fault; every request on that instance then ends with `400 Channel Error` or "The model has crashed without additional information", and LM Studio does not reload the model.
- **Metal's buffer limit:** `RuntimeError: [metal::malloc] Resource limit (499000) exceeded`. The engine's count of Metal buffers grows with the work an instance has done and is freed only when the instance is unloaded. Measured on an M5 Max and an M4 Pro, tokens processed (prompt and completion together) per instance since load: with short completions (1,700 to 2,300 tokens per request), three crashes at 931,000 to 1,175,000, and one instance served 1,354,000 without crashing; with long completions (3,100 to 4,300 tokens per request), crashes at 374,691 to 478,356 and once at 244,748, while one instance served 653,132. The longer the completions, the less work before a crash. The range is a hazard zone, not a hard limit.
- **Out of memory under long contexts:** `RuntimeError: [METAL] Command buffer execution failed: Insufficient Memory (00000008:kIOGPUCommandBufferCallbackErrorOutOfMemory)`. On the M5 Max (128 GiB, two instances of a 35.2 GiB model, 4 slots of 65,536 tokens each), replica 2 died 7 minutes after a recycle, having processed 404,635 tokens (395,711 of them prompt: 26 agent conversations of 18,000 to 44,000 tokens, which re-send their history) and holding some 110,000 tokens of context in flight while replica 1, back from its own recycle, read four more (about 70,000 tokens, one prompt of 43,664). The Mac's memory in use stood at 124.4 to 124.7 GiB for the two minutes before; other programs held about 22 GiB. The M4 Pro peer (48 GiB, GPU limit 40 GiB) died the same way three minutes later, freshly reloaded with four requests in flight. The engine keeps a KV cache per conversation (Qwen3.6-35B-A3B: 10 of its 40 layers, 2 KV heads × 256 × K and V × bf16 = 20 KiB a token), materializes attention scores while it reads a prompt (16 heads × bf16 × its 2,048-token step = 64 KiB per token of context), keeps the buffers it frees in a cache of its own, and plans each prompt against the whole GPU limit, which another engine process shares without its knowing.
- **Measured** under a batch of agent conversations (each engine's physical footprint every 3 s, read with `proc_pid_rusage`, against the requests in flight on it; 2,120 samples): above its weights an engine held 3.0 GiB with nothing in flight and 124 KiB more per token of context in flight (least squares; 20 KiB of it the KV cache), with peaks up to 16.5 GiB above its weights at 40,000 to 50,000 tokens in flight while it read a 20,000 to 30,000-token prompt (p99 per 10,000-token bin: 9.4, 9.1, 11.2, 12.3, 15.9 GiB). The engine's own formula (weights, 3 GiB, the KV cache and the attention scores) fell short of the footprint in 87% of the samples, by up to 11 GiB: its buffer cache. Other programs held 17.9 to 25.0 GiB. With nothing else running (`tools/loadbench.py --memory --direct` in a maintenance window: replica 2 alone, fresh prompts of 16,000 to 48,000 tokens, 1, 2 and 4 at once, 256-token answers), from 15,437 to 126,386 tokens held at once the peak footprint was 4.9 to 11.4 GiB above the weights, about 3.9 GiB + 52 KiB per token, with at least 20.2 GiB free: the cost with nothing competing. Agent conversations under a batch (prompt-cache restores, prompts read while other conversations decode, longer answers) took more than twice that per token, so the budget below is sized from the batch. Metal's own figure for what the GPU may hold (`recommendedMaxWorkingSetSize`): 107.5 GiB on the M5 Max (84% of its memory, `iogpu.wired_limit_mb` unset), 40 GiB on the M4 Pro (set to 40960).

**What the hub does** (`localmodels/crashes.py`, `recycle.py`, the gateway):
- The instance manager tails LM Studio's log as it is written. A crash is "The model has crashed" under a request's error on that model, or an instance of a configured family that disappeared with no unload line in the log (its engine died, LM Studio restarted or was updated, or it was ejected in LM Studio's window, which logs nothing: a configured family is meant to stay loaded, so it is back within a minute; `localmodels use <other model>`, or removing the family from the settings, changes that). A model unloaded with `lms unload` (which logs "Unloading model"), with `localmodels use`, or through the gateway's `POST /api/v1/models/unload` is left alone: LM Studio's REST API logs no unload line, so the hub marks the instances its own swaps and the gateway's forwarded unloads took as unloaded on purpose. An instance named in a crash line is down regardless of the model listing in hand; an instance that merely seems missing counts as missing only when LM Studio's own server does not list it either, no request is running on it, and two polls 20 s apart agree (`lms ps` is slow under load).
- It reloads the model with its previous load parameters: a family with its settings from `models.json`, another model with the parameters it had. It polls every 20 s, and immediately when a request through the gateway fails. An instance loads in about 10 s; a failed load is retried after 1, 2, then 5 minutes.
- **While one replica is down, the others keep serving**: the gateway routes around it, and holds a request (up to 10 minutes) only when no instance is left that could serve it.
- **A request that fails because the model crashed is resent by the gateway** once the model is back: a non-streaming one, or a streaming one before its first byte. This includes LM Studio's `400 Channel Error` and the engine's other failure words, which every request in flight gets when the generation thread dies, while the instance may still be listed for a moment: one list (`crashes.ENGINE_WORDS`) that the gateway and the log reader share, from Metal's `Insufficient Memory`, `kIOGPUCommandBufferCallbackError…` and `[METAL]` to `Resource limit`, the signals and `Channel Error`; a `5xx` in those words counts too. If that fails too, the client gets `503` with `Retry-After: 30`, never LM Studio's `400 The model has crashed` or a bare `502`. A genuine `400` passes through, and LM Studio's refused load ("insufficient system resources") is not an engine failure. A model the instance manager has stopped reloading gets `503` immediately. A truncated stream ends with an error event in its API's format (and `data: [DONE]` on OpenAI-style streams).
- **Admission by context size** (`admission.py`), so several long conversations at once never run an instance, or the Mac, out of memory (KV-cache-aware admission, as in vLLM's scheduler or text-generation-inference's `max_batch_total_tokens`). The gateway estimates each request's context before LM Studio reads it: its prompt from its body's size, at the bytes per token measured on this Mac's recent requests (the lower quartile, so estimates err high), plus its `max_tokens` (at most 4,096 counted). Each instance has a **budget of context in flight**: its share of what the Mac has for its models (its memory, less what other programs hold, measured every 10 s from the engines' footprints, less `headroom_gb`; or Metal's GPU limit less 2 GiB, whichever is less), less its weights, at the model's cost per token (its KV cache and attention scores, from its `config.json`: 84 KiB for Qwen3.6-35B-A3B), between 16,384 tokens and all its slots' windows. Beside a sibling it also counts the 3 GiB its engine keeps and its buffer cache (× 1.4: 118 KiB a token), which the other engine cannot reclaim; an engine alone reclaims its own at the GPU limit. That comes to about 95,000 tokens per instance on the M5 Max with two instances and other programs at 22 GiB, and about 35,000 on the M4 Pro peer, which held 40,000 to 60,000 tokens in flight at its 40 GiB GPU limit (39.5 to 40.7 GiB in use) and died at about 80,000. An instance with nothing in flight takes any request; a busy one takes a request while its context in flight plus the request fits its budget and, beside a sibling, while the Mac's free memory, less what the request takes, stays above `headroom_gb` (an engine alone fills memory up to its GPU limit with a cache it reclaims itself: the M4 Pro ran at 2.4 to 3.7 GiB free under the batch, so there the budget alone applies). The budget follows the memory other programs take (read every 10 s); requests already running are never stopped, so an instance may hold more than a budget that has just shrunk until they end. A request that fits nowhere waits in the admission queue (its in-flight marker and its log row say why: `wait_for`) while shorter requests behind it take the room there is; after 20 s it keeps its place on every instance it wants, so it is never starved. A peer reports its budget and the context in flight there, and the front sends it only what fits. Replayed against the requests before the crash above, these rules hold 12 of 98: the ones that took an instance past 95,000 tokens in flight (among them the 43,664-token prompt onto the freshly reloaded replica 1, and the request started 8 s before the crash) and one at 3.4 GiB free. Per family in `models.json`: `"admit": {"tokens": N}` sets a budget; `"admit": false` turns it off. `localmodels` and the dashboard show each instance's context in flight against its budget.
- At most 3 reloads of one instance within an hour. An instance that crashes again after that, or cannot be reloaded within an hour, leaves its family unloaded for an operator: the dashboard says so at the top with the command to reload it manually, `localmodels use <model>`; the instance manager retries every hour, each try with an hour of its own to load it; a family still down leaves the dashboard (and stays in `localmodels crashes`) a day after it was first left down; the other replicas keep serving. A crashed instance serves again as soon as it is reloaded, even while a sibling still waits for memory (the sibling is then loaded as a missing replica, when it fits).
- **Recycling before the crash** (`recycle.py`). Each instance is recycled at **300,000 tokens processed or 150,000 tokens written since load**, whichever comes first (drain: no new requests are routed to it, in-flight requests complete, it is unloaded and reloaded in about 15 s while the other replica serves), or at **73% of that whenever it is idle** (no drain needed), one instance at a time, two minutes apart, never while its family has an instance down. The processed count includes the context of the requests in flight on the instance (their estimates), so prompt-heavy work drains an instance before its requests in flight carry it past the threshold, not after (the replica above crossed 300,000 within four minutes of a fresh load and reached 404,635 before its drain began). An instance past its threshold drains 30 s after its sibling's recycle rather than two minutes, since its sibling's drain sent it every request; an instance that crashes while it drains comes back fresh from the crash reload, which ends the drain ("recycle given up: crashed while draining" in `localmodels crashes`). A batch requests fresh instances when it starts (`POST /hub/recycle`, which `agent.batch` and `localmodels recycle` send): an instance past half its threshold is recycled first. Per family in `models.json`: `"recycle": {"tokens": 300000, "written": 150000, "soft": 220000, "before_batch": 0.5}` (`false` disables it; `"written": 0` counts only tokens processed; `soft` is a share of `tokens`, applied to whichever count leads). With long completions every crash measured came at 197,524 to 213,269 tokens written while tokens processed ranged from 295,340 to 478,356, so the written count is the closer predictor; the drain threshold leaves room for the requests in flight (four completions of 10,000 tokens add 40,000 written before the unload). LM Studio's server resolves an unload by name to the oldest-loaded instance of that model key (measured with its REST API's `instance_id` and with `lms unload` alike), and a family's first replica is named by its model key: so the first replica is recycled only when it is the oldest instance, and an older sibling is recycled first. After every unload the instance manager also checks which instance went: if LM Studio took another one, that one is loaded again at once (the gateway resends its requests), the drained one keeps serving, and the recycle is retried after 10 minutes ("recycle given up" in `localmodels crashes`). This is what web servers do with workers that leak (gunicorn's `max_requests`); the reload and the resend remain the safety net, since an instance may still die below the threshold. Each instance's tokens since load, against its threshold, are on the dashboard, in `localmodels` and in `localmodels recycle --status`.
- Each crash and recycle goes in `crashes.jsonl`: time, model, LM Studio's own error text or the recycle's reason, the tokens that instance had processed since load, and what the hub did. Never content. See them on the dashboard, with `localmodels crashes` (`--scan` finds older ones in LM Studio's logs), and as a line in `localmodels` when one occurred in the last day.
- While any client is using a model, the gateway keeps the Mac awake (`caffeinate -i`), releasing it ten minutes after the last request.

**What a client should do:** nothing special. Send requests through the gateway; a request that gets `503` can be resent after `Retry-After` seconds (the local agents do this themselves for up to an hour). Do not hold a slot lock of your own for a request sent through the gateway.

**Open:** no single per-instance count separates every crash from every survivor (one instance survived 286,000 tokens written), but with long completions the crashes cluster within 8% of 205,000 tokens written, so the thresholds sit below the lowest crash under the heaviest load. `localmodels crashes` lists each instance's tokens before a crash and each recycle. One instance run alone at fixed completion lengths (1,000, 4,000 and 8,000 tokens) until it crashes would fit the curve; until then the reload and the resend are the safety net. The admission budget's cost per token and the 3 GiB an engine keeps were measured on one model and one LM Studio engine; another model's cost is computed from its `config.json` with the same 1.4 for the engine's cache, which a measurement on that model should confirm.

## Local agents
- **From a Claude Code session:** the `local-models` MCP tools. `ask` runs one question on the loaded model, with read-only tools scoped to this session's project folder, and blocks for up to two minutes. `batch` runs many jobs in parallel and returns a job id immediately; poll it with `job_status`. `folder` may name a folder inside the session's project (a worktree session's project is its main checkout), never one outside it; `job_status` reads only the jobs this project started.
- **From a terminal:** `localmodels ask "<question>" [--dir FOLDER] [--no-files] [--no-think]`, `localmodels batch jobs.json [--parallel N]`, `localmodels jobs`. `--dir` takes any folder inside the home folder except the home folder itself, `~/Library` and the home folder's dot-folders (`~/.ssh`, `~/.aws`, `~/.claude`, ...), as the MCP tools do.
- **From a project's own code:** `from localmodels import agent` gives `agent.run_job` and `agent.batch` with the project's own tools (`defs(job)` returns MCP-style tool definitions, `call(name, args, job)` runs one).
- A local agent only reads; it never writes. Its tools are `read_file`, `list_files` and `grep`, inside the folders it is given and nowhere else. Its answer is text, or JSON matching a schema; a script or a person verifies it before anything changes. Models fabricate quotes and line numbers, so check every quote against the files.
- Logs: `~/Library/Logs/LocalModels/agents/<project>/`, one folder per job: `plan.json`, a `.running` file per job in progress (the dashboard reads it), one `.json` per completed job, `summary.json`. These job logs hold the prompt and the answer: they are the project's own record of the job, unlike the hub's request records, which never hold content. `localmodels prune [--days 30]` removes the folders and logs older than that (a batch still running is kept).
- A job: `{"label": "...", "prompt": "...", "schema": {JSON Schema} or null, "max_turns": 16, "max_tokens": 4000, "think": true, "think_schema": false, "retry_empty": 1, "nonempty": false, "wait_down": 3600}`. `"think": false` for lookups and extraction, which complete several times faster; thinking on for checks and judgment (*Thinking*, below). The final step, the answer as JSON matching the schema, runs with thinking off whatever `think` says (`think_schema: true` overrides). An answer whose lists are all empty (whatever its other fields hold) is requested once more without the strict format (the schema in the prompt only), and that answer stands if it matches the schema all the way down (types, required fields, items, enums, `minItems`), else the empty one does (counted as `invalid` in the job's usage); JSON is read from the first object or list in the answer, so words around it do no harm; `"nonempty": true` sets `minItems: 1` on every list from the first request, for answers that can never be empty (*Strict JSON*, below). A request that fails because the model is down is retried with increasing backoff for up to `wait_down` seconds in all. Two jobs with the same label get distinct ones (`a`, `a-2`). A batch requests fresh instances when it starts.
- `job_status` gives a line per job; `results=true` adds the answers (capped, so a 300-job batch stays readable), `label=...` one job's full answer. A runner that died is reported as such, with its log's tail.

## Records and privacy
- In `~/Library/Application Support/LocalModels/`: `models.json` (the settings), `slots/` (one lock per slot), `leases/` (which client holds which model), `inflight/` (each request in flight now), `requests.jsonl` (one line per request: time, project, session, kind, model, instance (`copy`), endpoint, status, seconds, queue time, token counts, the body's size in bytes and its estimated context (`bytes`, `ctx`), why it waited for room (`wait_for`), the step, and a note when the gateway resent or dropped it), `waits.jsonl` (queue waits over 2 s, slot timeouts, refused swaps), `crashes.jsonl` (each crash and recycle), `keeper.json` (the instance manager's state: what it last saw loaded and since when, its read position in LM Studio's log, any model down after a crash, the recycle in progress, the last load LM Studio refused) and, with peers, `link.json` (the gateway's last poll of each peer: state, families, slots; never content) and `peer-token` (the shared secret, mode 0600).
- Never a prompt, a completion, a file's contents or anything else a client sent, in any of those records. The one place content is kept is the local agents' job logs, as each project's own record under its name.
- The gateway listens on loopback only (127.0.0.1 and ::1) and rejects browser requests from other web pages (`Host`, `Origin` and `Sec-Fetch-Site` checks: from a browser, only the dashboard's own requests, an address typed in, and a link that opens the dashboard page; programs send none of these headers and are unaffected). A host that serves as a peer also binds a link listener on its Thunderbolt Bridge address: token required; inference endpoints, the model list and its peer report only (*Peers*).

## LM Studio: settings and measurements
Measured on an Apple M5 Max (128 GB) with LM Studio 0.4 and its MLX engine.
- **Server:** OpenAI- and Anthropic-compatible on `http://localhost:1234` (the gateway forwards there), plus its own REST API (`/api/v1/chat`) and `/api/v0/models` (state, `loaded_context_length`, capabilities). The `lms` command (`~/.lmstudio/bin/lms`): `server start`, `ps --json`, `load <key> --context-length 65536 --parallel 4 --identifier <id>`, `unload <id>`, `daemon up` (LM Studio without its window). `lms server status` and `lms daemon status` print their output on standard error, not standard output: read both streams (the hub queries the server itself over HTTP).
- **Models:** Qwen3.6-35B-A3B, 8-bit, is the default family in `models.json`: 89 tokens/s for a single request, 203 with four concurrent, 38 GB. A dense 70B holds about 0.3 MB of KV cache per token of context per conversation, so four long conversations can add 50 GB on top of the weights; mixture-of-experts models held far less in practice. Some models (Llama 3.3 70B under the MLX engine) emit tool calls as plain text: `agent.text_calls` parses those into calls.
- **Context 64k, 4 slots.** At 32k, long documents overflowed; at 64k a long document check used 64% of the window.
- **Malformed outputs:** with a strict JSON schema, LM Studio may put the JSON in `reasoning_content` instead of `content`, so read both. A model sometimes ends a turn with empty content: retry once.
- **Strict JSON outputs come back empty** in two ways. With thinking on (`tools/loadbench.py`, 32 requests in two layouts): the model returned `{"items": []}` in 1.5 s with 5 reasoning tokens for 9 of 16 requests in each layout, and wrote the JSON inside its think block for the rest; with thinking off on the same synthetic memos, 0 empty and every planted figure found. And with thinking off on real text (tables, bullets, short lines; 16 chunks requested twice four ways): the grammar lets the model close its list at the first token, and it did for 21 of 32 answers at temperature 0.7 and 17 of 32 at 0.3; `minItems: 1` on the list brought that to 0 of 32 with full answers; without the strict format, 2 of 32, both correctly empty. **So: schema outputs with thinking off; `minItems: 1` on any list that cannot be empty; otherwise, re-request an empty strict output without the strict format.** The agents do all three automatically.
- **Thinking:** Qwen 3.6 thinks by default, and LM Studio exposes only on or off. `reasoning_effort: "none"` turns it off; `"low"`, `"medium"` and `"high"` all mean on (LM Studio logs *Falling back to reasoning setting 'on'*); `"off"` is refused (400); `chat_template_kwargs: {"enable_thinking": false}` is ignored. On four everyday jobs run three times each (`tools/thinkbench.py`), thinking off was 1.1 to 7 times faster and generated a sixth of the tokens (93 s of generation against 305 s in all); as accurate on extraction and on finding things in a folder with tools (9 of 9), but it missed a wrong sum in 2 of 3 consistency checks that thinking caught every time. **So: thinking off for lookups and extraction, on for checks and judgment.** Re-measure when the model changes. Either way, send the model card's sampling parameters (the agents use temperature 0.7, top-p 0.95, top-k 20).

## Setting up and updating
- `localmodels install` does it all, and is idempotent. It writes the settings file from the repo's default if there is none, starts the gateway at login (a LaunchAgent, `com.local-models.hub`, running a copy of the code in `~/Library/Application Support/LocalModels/hub/`, because macOS keeps background processes out of `~/Documents`), registers the hub's MCP tools for every Claude Code session (`local-models`, user scope), adds one signpost line to `~/.claude/CLAUDE.md`, and puts `localmodels` on PATH. `--dry` prints the plan; `--no-claude` leaves Claude Code alone. Installed as a Claude Code plugin (`/plugin install local-models --marketplace matthaedo/local-models-hub`, then `/local-models:setup`), it runs `install --plugin`: the plugin provides the MCP tools and a skill with the rules, so nothing is registered and no signpost line is added.
- After changing the hub's code: `localmodels check` (the sandbox tests, the gateway, a request end to end), then `localmodels install`. It replaces the gateway's installed copy when no request is in flight (`--wait 480` waits up to 8 hours for that) and no load or recycle is half done; `localmodels` and the terminal dash report *stale code* until then. `localmodels start` on a running gateway does nothing; `restart` waits for quiet.
- `localmodels publish` runs the tests, `claude plugin validate` and the privacy check, then stamps the version into the code and the plugin manifest and commits those two files alone on the commit the checks read (it refuses when HEAD moved or anything was staged meanwhile), tags that commit and pushes it (the first time, `--remote <url>` names the empty GitHub repository to push to). Users of the plugin get it on `/plugin update`. `--dry` runs the checks and changes nothing.
- **The privacy check** reads what the push would make public: every commit no `origin` ref holds yet (all of them before the first push), each on its own (the lines it adds, a merge's against each parent; the names of the files it adds or renames; its message; the message of an annotated tag on it), against a word list that never enters the repo: `~/Library/Application Support/LocalModels/private-words.txt`, or the file `LOCALMODELS_PRIVATE_WORDS` names. One regular expression per line, case-insensitive; `allow: <pattern>` for text that may go public though it contains a listed word; `#` for comments. On a match it lists each one with the commit that holds it and pushes nothing. A later commit does not clear a hit, since the push sends the earlier one too: amend, squash or rebase the commit named. A git command that fails stops the release; with no word list it reports the check as skipped.
- `localmodels uninstall` undoes all of it; the repo and the settings file are untouched.

## Troubleshooting
- `localmodels check` tests the gateway, LM Studio through it, the model listing, the `lms` command, the sandbox tests (instance manager, recycle policy, gateway, agent engine), the naming, a request end to end, the MCP tools and whether the gateway runs the current code.
- The gateway's log: `~/Library/Logs/LocalModels/gateway.log` (instance manager actions, every server start it issued and why, and any gateway error with its traceback).
- A client the dashboard flags *direct to LM Studio* is still calling port 1234: point it at 1235.
- A peer that is unreachable, fails auth or is excluded: `localmodels peer test` (gateway poll, terminal probe, route), and *Peers* above.
- A `503` from the gateway means the model is not responding and the instance manager is reloading it, or has stopped reloading it, or the request's own wait budget expired; the error text says which, and `Retry-After` says when to retry. `localmodels crashes` has the details.
- The dashboard's LM Studio chip turns yellow when the model listing is stale (`lms ps` failed or returned partial output under load): the hub then keeps the last complete listing and changes nothing until a complete one arrives. A settings file that cannot be parsed is reported on the status line and the dashboard; the last valid settings remain in effect.
