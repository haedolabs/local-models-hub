# Using the local models through the hub

## Now
- One LM Studio on this Mac is shared by every project and every Claude Code session through this hub. The rules live here, once; other projects get a signpost to this file.
- **Send requests to `http://localhost:1235/v1`**, the hub's door: the same API as LM Studio's (`/v1/chat/completions`, `/v1/models`, `/api/v0/models`, …). Never straight to LM Studio's port 1234.
- **Using a model is the check-in.** The hub names your project from your program's folder and your Claude Code session from Claude Code's own ids. There is nothing to report.
- **A family of copies is one model.** With the default settings `qwen/qwen3.6-35b-a3b` runs as two copies of four answers at once: ask for it as one model and the door picks the copy. **A batch should send as many requests at once as the loaded copies answer** (the `status` tool and `localmodels` say how many); the rest wait their turn.
- **Bulk reading jobs go to local agents** (the `local-models` tools `ask` and `batch`, or `localmodels ask`), not to multi-agent Claude workflows. Their answers are leads to check, not verdicts.
- **Never stop LM Studio's server.** Before unloading or reloading a model, run `swap_check` (or `localmodels swapcheck`). If it names anyone, don't swap.
- **If a model crashes, the hub loads it again** within a minute (at most 3 times an hour per copy); the other copies keep answering meanwhile, and a request that was being answered is sent again once the model is back. You get an answer, or `503` with `Retry-After` if it failed twice, never LM Studio's `400`. The hub also **recycles each copy before the amount of work at which the engine has crashed**, one copy at a time, so a long batch keeps going.
- **A person goes first.** When every slot is busy, the next free one goes to a `chat` or `ask` request before queued batch requests. Say `X-Kind: chat` when a person is waiting. The lane is cooperative, like everything here.
- **Turn LM Studio's just-in-time model loading off** (its developer settings). The door never needs it; with it on, a request for a model with nothing loaded could make LM Studio load a copy with its own settings. The door refuses such requests (`503`) rather than forward them, and the keeper recycles a copy with the wrong settings, but off is simpler.
- **Other Macs (peers).** A host linked by Thunderbolt can run the same hub and serve replicas of a family: the gateway routes requests to a peer's free slots by the slot order in *Peers* (batches spread across hosts, interactive requests stay local first), and responses return through this gateway. Clients change nothing. *Peers*, below, has the rules and the setup.
- **See it:** the dashboard at **http://localhost:1235** (`localmodels open`): every project and session using the models, each copy's slots and its work against its recycle band, charts over the last 15 minutes to 24 hours. In a terminal: `localmodels` (a few lines) or `localmodels dash` (live).

## Where to send requests
- Base URL `http://localhost:1235/v1` for any OpenAI-style client (the Python `openai` package, `curl`, LangChain, an app's "custom endpoint" field), or `http://localhost:1235` for an Anthropic-style client (the `anthropic` package's `base_url`; it calls `/v1/messages`). LM Studio's own REST API works the same way at `/api/v1/...`. The API key can be anything.
- Every API takes turns the same way, and its token counts feed the dashboard and the recycle band alike. When the door itself refuses a request (`503` while waiting for a turn, `409` during a swap), the error on `/v1/messages` is shaped as Anthropic's (`overloaded_error` for a `503`), so Anthropic's SDKs retry it; on the other paths it stays `{"error": "..."}`.
- The door passes everything to LM Studio unchanged, streaming included. The difference is that it takes turns: all programs together never send a model more requests than it answers at once (its *Max Concurrent Predictions*), so a request may wait for a free slot instead of piling up behind others until it times out.
- **Copies.** A family in `models.json` is loaded as `<id>`, `<id>:2`, … with the same context and the same answers at once. A request for the family id goes to the first copy with a free slot (the first copy's slots fill before the second's); a request naming one copy goes to that copy while it is loaded, else to its siblings. The answer names the model asked for.
- **Measured** (Apple M5 Max, 128 GB; LM Studio 0.4; Qwen3.6-35B-A3B 8-bit, 65,536 context, 4 at once per copy): on short answers, 4 at once wrote 209 tokens a second in all and 8 at once on two copies 252; on long prompts with long strict-JSON answers (`tools/loadbench.py`), two copies with 8 at once wrote 193 tokens a second while every slot was busy against 156 for one copy with 4 — 23% more in all, at 1.7 times the time per request (median 177 s against 106 s). Two copies serve batches; a person waiting is better served by the queue putting chats first than by a third copy.
- The keeper loads a family's other copies whenever its first copy is loaded, if they fit in memory. It never loads a model from nothing (a Mac with no model loaded stays free), except a model that crashed, and never unloads one for being idle; it does recycle a copy (unload and load it again with nothing in flight on it) before the band in which the engine has crashed, and brings a copy loaded with other settings than the family's back to them. The settings live in `~/Library/Application Support/LocalModels/models.json` (`families`: copies, context, parallel, `recycle`; `batch_at_once`; `headroom_gb`); a fresh install writes it fitted to the Mac's memory and downloaded models, starting from the repo's measured default `localmodels/models.json`.
- If LM Studio's server is off (LM Studio turns it off when the model is changed in its window), the door starts it and tries once more. It never starts a server that is already up: that restarts it and cuts every request in flight. If the door itself is closed, `localmodels start` opens it. Code that must keep working without the hub can use `llmshare.post`: through the hub when it is up, straight to LM Studio holding a slot when it is not. (`LMSTUDIO_URL` is LM Studio's own address for the hub's code, port 1234, never the door's; a project's code finds the door at `llmshare.HUB`.)
- **Never hold a slot of your own (`llmshare.slot`) for a request you send through the door.** The door takes a slot for it, and the two would wait on each other.
- A program that hangs up while its request waits for a turn is dropped, not sent (the log says `hung up`); one that hangs up during a long answer makes the door hang up on LM Studio too, which stops generating.
- A program that says how long it will wait (`X-Timeout: <seconds>`; `llmshare.post` sends its own timeout) gets `503` with `Retry-After` at nine tenths of that, so the door's wait never outlives the program's.

## Naming a request (optional)
- Nobody has to. The project is the first folder under `~/Documents` (or `~/Projects`, `~/Developer`, …) that your program runs in, so a worktree counts as its project. The Claude Code session comes from the ids Claude Code puts in every shell and tool it starts.
- To name it yourself: header `X-Project: <name>`, or put it in the path (`http://localhost:1235/p/<name>/v1`, for apps that only let you set a URL).
- To say what kind of run it is: header `X-Kind:` `batch`, `chat` (a person is waiting), `ask`, `eval`, `test` or `other`. The dash shows it, and `chat` and `ask` go first when slots are scarce.
- To say what a request is for: header `X-Step: reading chapter 3` (a few words). The dash shows it next to the request; the local agents send it themselves.

## A batch's progress and time left
- **A program that runs a batch says so with three headers on each request**, from any language, no library needed. The dash then shows a progress bar and the time left, and `localmodels` says it in a line:
  - `X-Run: nightly-extract`: a name for the whole run, the same on every request of it.
  - `X-Run-Total: 420`: the units of work in the whole run, every phase together. It may rise as the program learns more (a phase whose size is known only when the one before ends).
  - `X-Run-Done: 17`: the units finished so far, as the program counts them.
- The program counts because only it knows what a unit is: an item may take several requests, a retry, or an agent's back-and-forth. Keep `X-Step` for the phase it is in (`extract files 8 of 360`); the dash shows both.
- **Without the headers**, a step that reads `<phase> N of M` still shows that phase's progress: items whose request was answered count as done.
- **The time left is measured on this Mac, never assumed:** the pace of the last 15 minutes or the last 20 units, whichever reaches further back, so it follows a run that speeds up or slows down. Before 3 units are done it uses the last run of the same name; the first time a name runs, it says it is estimating until the pace shows. Keep a run's name the same from one run to the next so the estimate starts right.
- A pause of 20 minutes between requests starts a new run of the same name. A run with no request for 15 minutes is no longer shown.
- The hub logs the run's name and the two numbers with each request, nothing else about it.
- `X-Session` is a free tag for the request log (the measurement tools use it to tell runs apart).

## Long runs: a lease
- The hub counts a program as using a model from its first request until two minutes after its last, so no swap pulls the model out between two steps of a run. That covers most work with no code at all.
- A run that pauses longer, or that should show its progress on the dash, holds a lease:

```python
import os, sys; sys.path.append(os.environ.get('LOCALMODELS_HOME', '<where the hub is checked out>'))
from localmodels import llmshare
with llmshare.lease('<project>', [model], 'batch', log_dir=folder) as run:   # log_dir: optional, see local agents
    run.step('reading the second file')        # optional: what it is doing, on the dash at once
    reply = llmshare.post('/v1/chat/completions', body, '<project>', 'batch')
```

- A lease holds the project's name, the model ids, a kind and the Claude Code session if there is one. It never holds a prompt, a file name or any content.

## Names on the screens
- **Every screen shows names the person chooses:** the dash, `localmodels`, `localmodels log`, the terminal dash and the `status` tool. The hub records what a program or folder calls itself (`X-Project`, else its folder); `~/Library/Application Support/LocalModels/names.json` maps that to what is shown, at the moment a screen reads, so a new name applies to all past history.
- `localmodels name` lists every project as seen and as shown, with the batches (`X-Run`), jobs (the phase in `X-Step`) and scripts it has used. Then:
  - `localmodels name project <as seen> <shown>`: what every screen calls a project. Several names seen can show as one, e.g. a folder and the `X-Project` its scripts send.
  - `localmodels name batch <project> <as seen> <shown>`: a name for one of its batches, jobs or scripts.
  - `localmodels name private <project>` (and `public`): the screens show only the names set for it, with no Claude Code session titles and no unnamed scripts, free-text steps or batch names. A count such as `8 of 360` stays.
  - `localmodels name forget <project> [<as seen>]`: drop one label, or the whole entry.
- A program can still name itself and its batch (`X-Project`, `X-Run`); the person's names apply on top.

## Maintenance
- **The person running the Mac sets it:** `localmodels maintenance in 15m for 30m updating LM Studio` (or `at 20:30`, `now`, or `after-batches`, which starts once no batch has sent a request for 2 minutes). `localmodels maintenance` alone says what is set and which batches would run into it; `localmodels maintenance off` ends it.
- **Announced** (before it starts), everything works, and the hub says it everywhere: every answer from the door carries the header `X-Hub-Maintenance` (`announced; starts=<local time>; until=<local time>; minutes=30; why=...`), the dash shows it at the top and flags a batch or job due to finish after it starts, `localmodels` and the `status` tool say it, `/hub/health` has it, and a Claude Code hook adds one line to every session's next prompt.
- **On**, a new request gets `503` with `Retry-After` set to the expected end and the same header; a request already being answered finishes; one still waiting for its turn is refused when its turn comes. The door never starts LM Studio's server and the keeper loads, reloads and recycles nothing, so the hub never works against the person updating or restarting LM Studio.
- **Off**, what LM Studio logged meanwhile is not read as crashes, and each model that was loaded when maintenance began is loaded again (its copies follow).
- **A program:** read `X-Hub-Maintenance` on any answer. When it says `announced`, finish the item in hand and do not start work that would run past `starts`. On `503` with `Retry-After`, sleep that long and carry on where it left off; do not count it as a failure. The hub's own local agents already wait out a `503` for up to an hour.
- **A Claude Code session** that gets the notice does not start a local-model batch that would run into it, and tells the person.

## Swaps (unloading, reloading, a context change)
- The simplest swap: `localmodels use <model>` (add `--dry` to see what it would do). It refuses while another run is using anything it would unload, unloads the rest (every copy of a family, so the other model has the room), and loads the model; `localmodels use <family>` brings all its copies back.
- By hand, before `lms unload`, `lms load` with another context, or a model switch: `localmodels swapcheck <model>` (exit 0 = safe), the `swap_check` tool, or `llmshare.swap_blockers([model])`. If it names a run, don't swap: say who is using it and stop. If `lms ps` doesn't answer, don't swap either. A run on one copy blocks a swap of any copy of its family.
- The door refuses a load or unload sent through it while another run is using the model (answer 409, with who is using it).

## Peers: other Macs over Thunderbolt
- **Model.** Every host runs its own hub (gateway + instance manager). The host the clients use (the front) lists peer gateways under `peers` in its settings; a host that serves as a peer sets `serve` (the address of its link listener). A family loaded on a peer is one more replica of that family: admission takes local instances first, then peer replicas, through the same admission queue (interactive requests first, then FIFO). Clients change nothing: they keep sending to `http://localhost:1235`, and responses name the model requested.
- **Capacity.** The front polls each peer's `GET /hub/peer` every 2 s: per family, its instances, total slots, busy slots, and how many of those this front holds. The front never has more requests in flight on a peer than `slots − (busy − this front's)` at the last poll. `localmodels`, the `status` tool and `llmshare.at_once` include that capacity, so a batch sized by them also fills the peers.
- **Slot order.** Batch requests (every kind except `chat` and `ask`) fill each host's first instance before a second instance on any one host: local instance 1, the peers' first instances, local instance 2, then the remaining peer slots. Interactive requests (`chat`, `ask`) take local instances first (lowest per-request latency) and peer replicas only when local slots are full.
- **Measured** (Qwen3.6-35B-A3B 8-bit, LM Studio 0.4, MLX; `tools/loadbench.py` extraction load: 16 requests, long prompts, strict-JSON outputs, thinking off, up to 10,000 tokens each; peer on a Thunderbolt 5 cable):

  | | output tokens/s, all slots busy | per request | median latency | p90 |
  |---|---|---|---|---|
  | Apple M5 Max (128 GB), 1 instance × 4 slots | 156.4 | 39.1 | 106 s | |
  | Apple M5 Max, 2 instances × 4 slots | 192.6 | 24.1 | 177 s | |
  | MacBook Pro M4 Pro (16-core GPU, 48 GB), 1 instance × 4 slots | 73.3 (70.5 wall-clock; 57.9 prompt tokens/s) | 18.3 | 237 s | 282 s |

  The peer recalled 1,490 of 1,492 planted figures (0 empty, 0 errors, 0 fabricated), the same accuracy as the M5 Max. One peer instance delivers about 47% of one M5 Max instance, and adds nearly all of it on top of the M5 Max's two instances (192.6 + 73.3 ≈ 266 tokens/s, +38%), since its GPU and memory bandwidth are independent; a second instance on the same host added 23%. Hence the slot order: independent hosts before stacked instances for batches, the fastest local slot for interactive requests.
- **Model identity.** A peer's instances are replicas only when they match this host's fingerprint: the family id in settings, the loaded variant (`lms ps --json` `selectedVariant`, e.g. `qwen/qwen3.6-35b-a3b@8bit`), size in bytes, format, and a digest of the model definition (`~/.lmstudio/hub/models/<key>/model.yaml` and `manifest.json`, which carry the prompt template, including the thinking switch, and the sampling config). Another quantization under the same key is another model. Weights copied without their definition load under another key with no template, and strict-JSON outputs come back empty. A family never loaded on this host has no local fingerprint; `"variant": "<key>@<quantization>"` in the family's settings pins the accepted variant. The dashboard shows why a replica is excluded.
- **Attribution.** The front forwards `X-Project`, `X-Session`, `X-Kind`, `X-Step`, `X-Run`, `X-Run-Total` and `X-Run-Done`, plus `X-Hub-From` (its gateway name). The peer logs the request under that project with `from: <front>`, holds a lease for it (a swap on the peer is refused while the front's batch uses the model, and the refusal names the front), and shows it on its own dashboard. The front logs it with `copy: "<family> on <peer>"` and `peer: <name>`, so the front's recycle accounting never counts peer tokens against a local instance.
- **Failure handling.** If a peer cannot take a request (ECONNREFUSED, maintenance, auth failure, or no free slot within 5 s: the front sends `X-Timeout: 5`), the peer responds before any byte reaches the client and the front requeues the request locally; the request log notes `requeued locally: ...`. An unreachable peer is polled again with exponential backoff (2 s, 4, 8 … 60 s); an auth failure is not retried until the token or settings change, or 5 min pass; a peer in maintenance is excluded until its window ends; three failed requests within 60 s back a peer off as if unreachable. TCP keepalive on peer connections detects a dead link mid-response within about 25 s; a stream already started then ends with an error event in its API's format.
- **Per-host scope.** Maintenance, recycling, crash recovery and the instance manager stay local to each host. This host's maintenance still rejects new requests even when a peer is up. Requests received over the link are served locally only (no multi-hop routing).
- **Link listener.** A host with `serve` set binds a second listener on that address, bound to its interface (`IP_BOUND_IF`). It accepts only requests carrying the shared token (`X-Hub-Token`, constant-time compare), rejects any with an `Origin` header, and serves only inference endpoints, the model list, `/hub/peer` and `/hub/health`; loads, unloads, recycles, maintenance and the dashboard are loopback-only. The token is one secret for the whole set of hosts, in `~/Library/Application Support/LocalModels/peer-token` (mode 0600), never in the repo or settings and never printed. It crosses the cable over plain HTTP, so the link assumes a direct cable between trusted hosts.
- **LM Link** (LM Studio's machine linking: preview, over its own Tailscale network, requires an LM Studio account) lets `localhost:1234` reach a model loaded on another machine. It does not load-balance one model across machines (with the model loaded on both, requests stay local), tracks no slots, and routes over whatever path its network picks rather than the Thunderbolt Bridge. The hub does not use it, and excludes from its listing any model LM Link reports from another machine (`lms ps --json` rows with `deviceIdentifier` set), so LM Link can stay on or off on either host.

### Setting up a peer
Example: the front (here) and a peer (a 48 GB MacBook Pro) joined by a Thunderbolt cable. Steps marked **(person)** need someone at that host: an administrator password, or a click in a dialog.

1. **Static addresses on the Thunderbolt Bridge (person, both hosts).** One cable gives each host two link-local interfaces (`bridge0` and a virtual "Ethernet Adapter"); traffic to a 169.254 address may route via the slower one (measured: about 42 MB/s against 1.7 GB/s over `bridge0`), and those addresses change on every reboot. Assign each host a static IPv4 address on the bridge, in a dedicated subnet, e.g. 192.168.213.1 here and 192.168.213.2 on the peer: System Settings → Network → Thunderbolt Bridge → Details → TCP/IP → Configure IPv4: Manually, subnet mask 255.255.255.0, no router. Or: `sudo networksetup -setmanual "Thunderbolt Bridge" 192.168.213.2 255.255.255.0` (on the peer; `.1` here). Verify: `ifconfig bridge0 | grep "inet "` on each host; from here, `route -n get 192.168.213.2` reports `interface: bridge0` and `ping -c 3 192.168.213.2` replies.
2. **The hub on the peer.** Python 3.9+ (Command Line Tools: `xcode-select --install`, **person**: one click), the repo, then `bin/localmodels install --no-claude` (omit `--no-claude` if Claude Code runs there too). Write the peer's settings (step 4) first: `install` keeps an existing settings file.
3. **The model on the peer, as LM Studio stores it.** Either download the same model in LM Studio there, or replicate it from here: `localmodels peer copy-model qwen/qwen3.6-35b-a3b <user>@192.168.213.2`, with LM Studio stopped on the peer (**person**, or `lms daemon down` there; the command refuses while it runs). A catalog model is four artifacts, and copying fewer leaves it listed twice or loaded without its template: the definition folder (`~/.lmstudio/hub/models/<key>/`), the variant's weights folder (under the downloads folder), its two records in `~/.lmstudio/.internal/model-data.json` (the catalog model, `source.type: hub`, `transitive: false`; the weights folder, `source.type: huggingface` with its repository, `transitive: true`, `source.file` marked undefined in the superjson meta), and the default load config (`.internal/user-concrete-model-default-config/<key>.json`). `copy-model` rsyncs the folders over SSH, merges this host's two records, as LM Studio wrote them, into the peer's `model-data.json` (its other records preserved, the previous file backed up) and copies the config; `--dry` prints the plan. Verify on the peer with LM Studio running: `lms ls` lists the model once, and `lms ps --json` reports the same `modelKey` and `selectedVariant` as here.
4. **The family in the peer's settings.** On a host where two instances do not fit, `install`'s generated settings may pick another model or none. Set the family explicitly in the peer's `~/Library/Application Support/LocalModels/models.json`: one instance, the context and slots it runs with (measured on the 48 GB MacBook Pro: 65,536 and 4), and a `headroom_gb` that leaves the instance manager room to load it (`install` sets 8 on hosts with 48 GB or more, which a 35 GiB model on 48 GB never has): `"families": {"qwen/qwen3.6-35b-a3b": {"key": "qwen/qwen3.6-35b-a3b", "copies": 1, "context": 65536, "parallel": 4, "load_at_start": true, "recycle": {"tokens": 800000, "soft": 560000, "before_batch": 0.5}}}, "headroom_gb": 4, "serve": {"address": "192.168.213.2"}`. `"load_at_start": true` is for a dedicated peer: at gateway start the instance manager loads the family if no instance of it is loaded, after starting llmster (`lms daemon up`) when LM Studio is not running and once the GPU wired limit and free memory allow; at most 3 attempts 30 s apart, then it reports the manual command. An instance unloaded later by an operator is not reloaded until the next gateway start.
5. **GPU wired limit on the peer (person, sudo).** By default macOS lets the GPU wire about 75% of RAM (36 GiB of 48); the model's 35.2 GiB (37.75 GB) plus KV cache needs more. `localmodels peer gpu-limit`, run on the peer, writes the LaunchDaemon `com.local-models.gpu-limit` (runs `/usr/sbin/sysctl iogpu.wired_limit_mb=40960` at load: total RAM minus 8 GiB, set at boot, before login and LM Studio) next to the settings and prints the four `sudo` commands that install it; on a host where it is installed, it verifies it. Until the next reboot: `sudo sysctl iogpu.wired_limit_mb=40960`, then restart LM Studio (it reads the limit at startup). The peer reports the limit, and both dashboards warn when a model exceeds it or fits only because it was raised at runtime without the LaunchDaemon.
6. **LM Studio's loading guardrail on the peer (person, in LM Studio).** For a model that nearly fills the GPU wired limit, only Off lets `lms load` through. Measured on the 48 GB MacBook Pro: the guardrail refused every `lms load` of this model at every context, under Relaxed, under Custom 42 GB, and with `"alwaysAllowLoadAnyway": true` (which affects only the UI's "Load anyway"; lmstudio-ai/lms issue 499); with Settings → Model loading guardrails → Off (`"modelLoadingGuardrails": {"mode": "off"}`), `lms load` succeeds. The instance manager enforces `headroom_gb` itself before every load. The peer warns on both dashboards before any load is refused (guardrail on and a model above 75% of the GPU wired limit). With the guardrail on, the instance manager cannot load the model at start or on crash recovery: it reports the refusal and does not retry until the guardrail setting or `iogpu.wired_limit_mb` changes, or an operator loads it. A single-instance family is recycled only when the guardrail is Off or the instance manager has loaded it on that host once (make before break).
7. **First load on a dedicated peer.** With `load_at_start`, the instance manager loads the model when the hub's gateway starts. A login LaunchAgent from before the hub (`~/Library/LaunchAgents/com.local-models.load-at-login.plist`) keeps that job while it is installed, and the instance manager defers to it; `localmodels install` retires it (`launchctl bootout`, plist removed; script and log kept) once a family has `load_at_start`, so exactly one loader runs. Without `load_at_start`: `lms load qwen/qwen3.6-35b-a3b --identifier qwen/qwen3.6-35b-a3b -c 65536 --parallel 4 -y`.
8. **Register the peer and the token, here.** `localmodels peer add macbook 192.168.213.2` adds the peer to this host's settings, creates `peer-token` (64 hex characters, mode 0600) if missing, and prints the `ssh` command that copies it to the peer (the token is never printed). Run that command.
9. **Enable the link listener on the peer.** `localmodels peer serve 192.168.213.2` (or `serve` in its settings, step 4). The gateway binds it within 5 s; `localmodels peer` on the peer shows the listener and its interface, warning when it is not the Thunderbolt Bridge or the address is link-local. **(person)** With the peer's application firewall on, macOS may ask whether python3 may accept incoming connections: Allow.
10. **Verify, here.** `localmodels peer test` forces a poll from the gateway and probes from the terminal. `reachable` means done. If the terminal connects but the gateway reports EHOSTUNREACH, macOS Local Network privacy is blocking the gateway: it runs as a LaunchAgent, and macOS 15+ may block such a process's local-network connections with EHOSTUNREACH and no prompt. **(person)** System Settings → Privacy & Security → Local Network → enable python3, then test again.

**(person)** With FileVault on, a rebooted peer runs nothing until someone logs in: the GPU-limit LaunchDaemon, the hub and the model load all wait for that login, and the front routes around the peer meanwhile.

`localmodels peer`, the dashboard and the `status` tool then show each peer: state, RTT and interface, its replicas as rows under the family with slots colored by project, and, at the top of the dashboard, anything an operator must fix. `localmodels peer remove <name>` and `localmodels peer serve off` revert it; the gateway rereads the settings within seconds, so none of this needs a restart.

The LaunchDaemon `localmodels peer gpu-limit` writes for a 48 GB host (deterministic; installed by a person with the commands it prints):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
	<key>Label</key>
	<string>com.local-models.gpu-limit</string>
	<key>ProgramArguments</key>
	<array>
		<string>/usr/sbin/sysctl</string>
		<string>iogpu.wired_limit_mb=40960</string>
	</array>

```

## When a model crashes, and recycling before it does
**The failure.** LM Studio's MLX engine can die with `RuntimeError: [metal::malloc] Resource limit (499000) exceeded`, then a segmentation fault; every request on that copy ends with "The model has crashed without additional information", and LM Studio does not load the model again. The engine's count of Metal buffers grows with the work a copy has done and is freed only when the copy is unloaded. Measured on the hardware above: three crashes at 931,000, 1,161,000 and 1,175,000 tokens processed (prompt and answer together) per copy since its load; one copy served 1,354,000 without crashing. The band is a hazard zone, not a wall.

**What the hub does** (`localmodels/crashes.py`, `recycle.py`, the door):
- The keeper reads LM Studio's log as it is written. A crash is "The model has crashed" under a request's error on that model, or a copy of a family in the settings that went away with no unload line in the log (its engine died, LM Studio restarted or was updated, or it was ejected in LM Studio's window, which writes no line: a family in the settings is meant to stay loaded, so it comes back within a minute; `localmodels use <other model>`, or taking the family out of the settings, is the way to change that). A model unloaded with `lms unload` or `localmodels use` leaves "Unloading model" and is left alone. A copy named in a crash line is down whatever the model listing in hand says; a copy that merely seems missing counts as missing only when LM Studio's own server does not list it either, no request is running on it, and two looks 20 s apart agree (`lms ps` is slow under load).
- It loads the model again as it was: a family with its settings from `models.json`, another model with the settings it had. It looks every 20 s, and at once when a request through the door fails. A copy loads in about 10 s; a load that fails is tried again after 1, 2, then 5 minutes.
- **While one copy is down, the others keep answering**: the door routes around it, and holds a request (up to 10 minutes) only when no copy is left that could answer it.
- **A request that fails because the model crashed is sent again by the door** once the model is back: a non-streaming one, or a streaming one before its first byte. If that fails too, the program gets `503` with `Retry-After: 30`, never LM Studio's `400 The model has crashed` or a bare `502`. A genuine `400` passes through. A model the hub has given up on answers `503` at once. A stream that breaks off ends with an error event and `data: [DONE]`.
- At most 3 reloads of one copy within an hour. A copy that crashes again after that, or cannot be loaded again within an hour, leaves its family down for a person: the dash says so at the top with the command to load it by hand, `localmodels use <model>`; the keeper tries once more every hour; the other copies keep answering.
- **Recycling before the crash** (`recycle.py`). Each copy is recycled at **800,000 tokens processed since it was loaded** (drain: nothing new goes to it, its requests finish, it is unloaded and loaded again in about 20 s while the other copy answers), or at **560,000 whenever it is idle** (no drain needed), one copy at a time, two minutes apart, never while its family has a copy down. A batch asks for fresh copies when it starts (`POST /hub/recycle`, which `agent.batch` and `localmodels recycle` do): a copy past half its band is recycled first. Per family in `models.json`: `"recycle": {"tokens": 800000, "soft": 560000, "before_batch": 0.5}` (`false` turns it off). This is what web servers do with workers that leak (gunicorn's `max_requests`); the reload and the resend stay the safety net, since a copy may still die below the band. Each copy's work since it was loaded, against its band, is on the dash, in `localmodels` and in `localmodels recycle --status`.
- Each crash and recycle goes in `crashes.jsonl`: time, model, LM Studio's own error words or the recycle's reason, how much that copy had answered since it was loaded, and what the hub did. Never content. See them on the dash, with `localmodels crashes` (`--scan` finds older ones in LM Studio's logs), and as a line in `localmodels` when there was one in the last day.
- While any program is using a model, the door holds the Mac awake (`caffeinate -i`), and lets go ten minutes after the last request.

**What a program should do:** nothing special. Send requests through the door; a request that gets `503` can be sent again after `Retry-After` seconds (the local agents do this themselves for up to an hour). Do not hold a slot of your own for a request sent through the door.

**Open:** the thresholds come from three crashes and one survivor. `localmodels crashes` lists each copy's work before a crash and each recycle; if a copy dies well below 800,000 tokens the limit is not cumulative, and the reload and the resend stand on their own.

## Local agents
- **From a Claude Code session:** the `local-models` tools. `ask` runs one question on the loaded model, with tools that only read this session's project folder, and waits up to two minutes. `batch` runs many jobs side by side and returns a job id at once; follow it with `job_status`.
- **From a terminal:** `localmodels ask "<question>" [--dir FOLDER] [--no-files] [--no-think]`, `localmodels batch jobs.json [--parallel N]`, `localmodels jobs`.
- **From a project's own code:** `from localmodels import agent` gives `agent.run_job` and `agent.batch` with the project's own tools (`defs(job)` returns MCP-style tool definitions, `call(name, args, job)` runs one).
- A local agent reads; it never writes. Its tools are `read_file`, `list_files` and `grep`, inside the folders it is given and nowhere else. Its answer is text, or JSON matched to a schema; a script or a person checks it before anything changes. Models invent quotes and line numbers, so check every quote against the files.
- Logs: `~/Library/Logs/LocalModels/agents/<project>/`, one folder per job: `plan.json`, a `.running` file per job at work (the dash reads it), one `.json` per job done, `summary.json`. These job logs hold the prompt and the answer: they are the project's own record of the job, unlike the hub's request records, which never hold content. `localmodels prune [--days 30]` removes the folders and logs older than that (a batch still running is kept).
- A job: `{"label": "...", "prompt": "...", "schema": {JSON Schema} or null, "max_turns": 16, "max_tokens": 4000, "think": true, "think_schema": false, "retry_empty": 1, "nonempty": false, "wait_down": 3600}`. `"think": false` for lookups and extraction, which come back several times faster; thinking on for checks and judgment (*Thinking*, below). The last step, the answer as JSON matched to the schema, runs with thinking off whatever `think` says (`think_schema: true` overrides). An answer that lists nothing is asked for once more without the strict format (the schema in the prompt only), and that answer stands; `"nonempty": true` puts `minItems: 1` on every list from the first ask, for answers that can never be empty (*Strict JSON*, below). A request that fails because the model is down is tried again with growing pauses for up to `wait_down` seconds in all. Two jobs with the same label get distinct ones (`a`, `a-2`). A batch asks the hub for fresh copies when it starts.
- `job_status` gives a line per job; `results=true` adds the answers (capped, so a 300-job batch is readable), `label=...` one job's whole answer. A runner that died shows as such, with its log's tail.

## What the hub keeps, and what it never keeps
- In `~/Library/Application Support/LocalModels/`: `models.json` (the settings), `slots/` (a lock per request a model answers at once), `leases/` (who is using which model), `inflight/` (each request passing through right now), `requests.jsonl` (one line per request: time, project, session, kind, model, copy, endpoint, status, seconds, time waited, token counts, the step, and a note when the door resent or dropped it), `waits.jsonl` (waits over 2 s, waits that ran out, refused swaps), `crashes.jsonl` (each crash and recycle), `keeper.json` (what the keeper last saw loaded and since when, how far it has read LM Studio's log, any model down after a crash, the recycle in progress, the last load LM Studio refused) and, with peers, `link.json` (the gateway's last poll of each peer: state, families, slots; never content) and `peer-token` (the shared secret, mode 0600).
- Never a prompt, an answer, a file's contents or anything else a program sent, in any of those records. The one place content is kept is the local agents' job logs, as each project's own record under its name.
- The door serves this Mac only (127.0.0.1 and ::1) and refuses requests from web pages of other sites. A host that serves as a peer also binds a link listener on its Thunderbolt Bridge address: token required, inference endpoints, the model list and its peer report only (*Peers*).

## LM Studio: settings and what was measured
Measured on an Apple M5 Max (128 GB) with LM Studio 0.4 and its MLX engine.
- **Server:** OpenAI- and Anthropic-compatible on `http://localhost:1234` (the door forwards there), plus its own REST API (`/api/v1/chat`) and `/api/v0/models` (state, `loaded_context_length`, capabilities). The `lms` command (`~/.lmstudio/bin/lms`): `server start`, `ps --json`, `load <key> --context-length 65536 --parallel 4 --identifier <id>`, `unload <id>`, `daemon up` (LM Studio without its window). `lms server status` and `lms daemon status` print their answer on standard error, not standard output: read both streams (the hub asks the server itself over HTTP).
- **Models:** Qwen3.6-35B-A3B, 8-bit, is the default family in `models.json`: 89 tokens a second alone, 203 with four at once, 38 GB. A dense 70B holds about 0.3 MB per token of context per conversation, so four long conversations can add 50 GB on top of the weights; mixture-of-experts models held far less in practice. Some models (Llama 3.3 70B under the MLX engine) write tool calls as plain text: `agent.text_calls` turns those into calls.
- **Context 64k, four at once.** At 32k, long documents overflowed; at 64k a long document check used 64% of the window.
- **Wrong-shaped answers:** with a strict JSON schema, LM Studio may put the JSON in `reasoning_content` instead of `content`, so read both. A model sometimes ends a turn with no words: retry once.
- **Strict JSON answers empty** two ways. With thinking on (`tools/loadbench.py`, 32 requests in two layouts): the model answered `{"items": []}` in 1.5 s with 5 reasoning tokens for 9 of 16 requests in each layout, and wrote the JSON inside its think block for the rest; with thinking off on the same synthetic memos, 0 empty and every planted figure found. And with thinking off on real text (tables, bullets, short lines; 16 chunks asked twice four ways): the grammar lets the model close its list at the first token, and it did for 21 of 32 answers at temperature 0.7 and 17 of 32 at 0.3; `minItems: 1` on the list brought that to 0 of 32 with full answers; without the strict format, 2 of 32, both rightly empty. **So: schema answers with thinking off; `minItems: 1` on any list that cannot be empty; otherwise, an empty strict answer asked again without the strict format.** The agents do all three on their own.
- **Thinking:** Qwen 3.6 thinks by default, and LM Studio gives it only on or off. `reasoning_effort: "none"` turns it off; `"low"`, `"medium"` and `"high"` all mean on (LM Studio logs *Falling back to reasoning setting 'on'*); `"off"` is refused (400); `chat_template_kwargs: {"enable_thinking": false}` is ignored. On four everyday jobs run three times each (`tools/thinkbench.py`), thinking off was 1.1 to 7 times faster and wrote a sixth of the tokens (93 s answering against 305 s in all); as right on extraction and on finding things in a folder with tools (9 of 9), but it missed a wrong sum in 2 of 3 consistency checks that thinking caught every time. **So: thinking off for lookups and extraction, on for checks and judgment.** Measure again when the model changes. Either way, send the model card's sampling (the agents use temperature 0.7, top-p 0.95, top-k 20).

## Setting the hub up, and changing it
- `localmodels install` does it all, and is safe to run again. It writes the settings file from the repo's default if there is none, opens the door at login (a LaunchAgent, `com.local-models.hub`, running a copy of the code in `~/Library/Application Support/LocalModels/hub/`, because macOS keeps background programs out of `~/Documents`), registers the hub's tools for every Claude Code session (`local-models`, user scope), adds one signpost line to `~/.claude/CLAUDE.md`, and puts `localmodels` on PATH. `--dry` says what it would do; `--no-claude` leaves Claude Code alone. Installed as a Claude Code plugin (`/plugin install local-models --marketplace matthaedo/local-models-hub`, then `/local-models:setup`), it runs `install --plugin`: the plugin brings the tools and a skill with the rules, so nothing is registered and no signpost line is added.
- After changing the hub's code: `localmodels check` (the sandbox tests, the door, a request end to end), then `localmodels install`. It refreshes the door's copy at a moment when no request is passing through (`--wait 480` waits up to 8 hours for one) and no load or recycle is half done; the dash says *runs older code* until then. `localmodels start` on an open door does nothing; `restart` waits for quiet.
- `localmodels publish` runs the tests, `claude plugin validate` and the privacy check, then stamps the version into the code and the plugin manifest, commits, tags and pushes (the first time, `--remote <url>` names the empty GitHub repository to push to). Users of the plugin get it on `/plugin update`. `--dry` runs the checks and changes nothing.
- **The privacy check** reads what the push would make public (every line added since the last release tag, every new file name, every commit message) against a word list that never enters the repo: `~/Library/Application Support/LocalModels/private-words.txt`, or the file `LOCALMODELS_PRIVATE_WORDS` names. One regular expression a line, case does not matter; `allow: <pattern>` for text that may go public though it holds a word; `#` for notes. On a match it lists each one and pushes nothing. With no such file it says the check was skipped.
- `localmodels uninstall` undoes all of it; the repo and the settings file are untouched.

## If something is wrong
- `localmodels check` tests the door, LM Studio through it, the model listing, the `lms` command, the sandbox tests (the keeper, the recycle policy, the door, the agent engine), the naming, a request end to end, the tools and whether the door runs the current code.
- The door's own log: `~/Library/Logs/LocalModels/gateway.log` (what the keeper did, every server start it issued and why, and any stumble of the door with its traceback).
- A program the dash flags *straight to LM Studio* is still calling port 1234: point it at 1235.
- A peer that is unreachable, fails auth or is excluded: `localmodels peer test` (gateway poll, terminal probe, route), and *Peers* above.
- A `503` from the door means the model is not answering and the hub is bringing it back, or has given up, or the request's own wait budget ran out; the words say which and the `Retry-After` header says when to try again. `localmodels crashes` has the story.
- The dash's LM Studio chip turns yellow when the model listing is unsure (`lms ps` failed or answered partially under load): the hub then keeps the last good listing and changes nothing until a good one comes. A settings file that cannot be read is said on the status line and the dash; the last good settings stand.
